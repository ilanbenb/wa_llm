# T01 — Extension shell and executable test harness

Status: planned. Owner: assigned coding agent. Reviewer: coordinating agent. Dependencies: none. Read [AGENTS](../../AGENTS.md), [SPEC sections 1 and 10](../SPEC.md), and [TESTPLAN evidence layers](../TESTPLAN.md).

## Goal

Create the smallest runnable Manifest V3 extension and automatic harness needed for subsequent tickets. Code lives at `projects/wa-scribe/` inside `wa_llm`; run npm commands from that project directory. Do not change the Python bot or create a nested Git repository.

## Scope

- Pin an exact tested Node 24 patch release in the runtime-version file and CI, plus actual compatible tool versions; npm with a committed lockfile. Add strict TypeScript, Vite, Vitest, Playwright, and Chrome API types. Avoid extra runtime dependencies and frontend frameworks.
- Production build emits an MV3 manifest, minimal side-panel page, background worker, and content entry. Use one small message contract and a plain-DOM panel.
- Add a synthetic local page and an unpacked-extension browser test using a persistent Chromium context. Fixture-origin permission belongs only in the test build, not the production artifact.
- Make an actual panel/worker/content exchange observable in the test. Validate the test message shape and sender/context; reject an invalid request. An empty panel screenshot, fake global `chrome`, or open-port assertion alone does not satisfy the browser case.
- Add `typecheck`, `test:unit`, `test:browser`, and `build` package scripts. Required test runs must fail if they discover zero tests. Keep ordinary automatic suites off real Google/WhatsApp networks.
- Add the dedicated `.github/workflows/wa-scribe.yml` at the shared Git root using the pinned runtime, `npm ci`, required checks, and the browser dependency installation appropriate for its runner. Set run-step working directories to `projects/wa-scribe`, use that project's version-file/cache paths, and filter triggers to `projects/wa-scribe/**` and this workflow. Leave the existing Python workflow unchanged. Ignore dependencies, build/test outputs, credentials, and user browser profiles.
- Update README with exact clean-install, test, build, and unpacked-load steps and prerequisites. CI is configured but not called remotely passed until a real run completes.

Suggested layout relative to `projects/wa-scribe/`, kept minimal:

```text
src/panel.html
src/panel.ts
src/background.ts
src/content.ts
tests/fixtures/chat.html
tests/browser/extension.spec.ts
```

Use a small additional message-contract module only if it avoids a duplicated contract. Config files/tests may require more files than a later feature ticket; do not invent an abstraction hierarchy to fill this layout.

## Out of scope

No Google OAuth/token flow, Drive writes, real WhatsApp DOM scraping or private endpoints, file grammar, media, reconciliation, persistent job engine, or pretend Sync success. The panel may say setup is not implemented. It must not claim chats are exported.

## Acceptance

1. From a clean checkout, install with the documented Node/npm versions and lockfile; all four scripts complete with meaningful checks/test counts.
2. Build artifacts load as an unpacked extension in the automated Chromium context; at least one valid contract interaction succeeds and an invalid request is rejected.
3. Browser tests demonstrably reach the built extension and fixture content script; no fake Chrome API object substitutes for the extension runtime.
4. Test-only fixture access is absent from the production manifest; no broad permissions or Google credential fields are added for later tickets.
5. README distinguishes automatic evidence, configured CI, and unrun real-browser/WhatsApp/OAuth checks.

If the installed browser cannot load the extension in the chosen runner, diagnose that prerequisite rather than replacing the browser test with a unit mock. Preserve evidence and return the concrete blocker while completing independent build/type/unit work.
